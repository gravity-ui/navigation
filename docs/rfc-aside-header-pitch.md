# AsideHeader compound: шпаргалка для презентации RFC

Спутник к [RFC](./rfc-aside-header-compound-components.md) (полные сигнатуры — в его [Приложении A](./rfc-aside-header-compound-components.md#приложение-a-спецификация-api)).
Читается сверху вниз по ходу доклада. Ориентировочный тайминг — 20 минут + вопросы.

---

## 0. Питч за 30 секунд

> `AsideHeader` — это один компонент с 32 пропами, «бог-контекстом» и семью разными способами что-то кастомизировать. Три вида пунктов, которые внутри оказываются одним и тем же кодом. Любая новая фича = правки в 5–7 файлах и ещё один проп.
>
> Предлагаю разложить его на compound-компоненты в стиле base-ui: явная композиция вместо скрытых рендер-функций, один `render` вместо семи механизмов, один список вместо трёх, узкие контексты вместо одного общего. Прототип готов и проходит линтеры, портированные сторис дают визуальное сравнение со старым компонентом.

---

## 1. Проблема в цифрах

Всё проверено по коду, ссылки в RFC §1.

| Метрика                                            | Сейчас                                                          | После                   |
| -------------------------------------------------- | --------------------------------------------------------------- | ----------------------- |
| пропов верхнего уровня                             | ~32                                                             | 7 у `Root`              |
| полей у типа пункта                                | ~35 (7 `@deprecated`, 2 `@internal`)                            | 13, ноль deprecated     |
| механизмов кастомизации                            | 7 разных сигнатур                                               | 1 (`render`)            |
| API для «пункта навигации»                         | 4 (`subheaderItems`, `menuItems`, `renderFooter`, `FooterItem`) | 1 (`Item` в `ItemList`) |
| контекстов                                         | 3, один из них «всё сразу»                                      | 6 узких                 |
| значений, которые читает `FirstPanel` из контекста | 17                                                              | — компонента больше нет |

**Одна фраза для слайда:** «Три публичных API рендерят один и тот же `Item`, отличаясь только местом и режимом overflow».

## 2. Семь ключевых фич

По одной на слайд. Для каждой: было → стало → зачем.

### 2.1 `render` вместо семи механизмов

**Было:** `renderContent`, `renderFooter`, `collapseButtonWrapper`, `itemWrapper`, `logo.wrapper`, `topAlert.render`, `renderPopupContent` — семь разных сигнатур.

**Стало:** один проп на каждой части.

```tsx
// было — надо знать про трёхаргументную сигнатуру и про то,
// что при itemWrapper корневой тег меняется с <button> на <div role="button">
itemWrapper: (params, makeItem, {collapsed, compact, item, ref}) => <Link …>{makeItem(params)}</Link>

// стало
<AsideHeader.Item id="projects" icon={FolderIcon} render={<Link to="/projects" />}>Projects</AsideHeader.Item>
```

**Зачем:** обработчики чейнятся (пользователь не может случайно убить внутреннее поведение), `className` склеиваются, refs объединяются. Одна семантика на весь компонент.

### 2.2 `ItemList` — один контейнер вместо трёх обёрток

**Было:** `Subheader`, `Menu`, `Footer` — три компонента, каждый со своей копией маппинга `items`. Клавиатурная модель разная: в меню roving tabindex, в футере и сабхедере — обычный Tab.

**Стало:** `ItemList` владеет фокус-моделью, ARIA-ролями, overflow и дефолтами. `Subheader` / `Menu` / `Footer` — пресеты в одну строку.

**Три бага, которые чинятся заодно:**

1. `role="menu"` без `menuitem` внутри — невалидный ARIA.
2. `Item` больше не ветвится на `place === 'menu'`: он регистрируется, если вокруг есть скоуп навигации.
3. `menuOverflow` / `menuMoreTitle` / `onMenuMoreClick` переезжают с корня на список и работают в любом списке.

**Формулировка:** «в списках — только пункты; всё остальное про список знает список».

### 2.3 `Item` / `GroupItem` / `Divider` — три разные сущности

**Было:** `Item` с полем `type: 'divider'` и полем `items` для вложенности. Разделитель без `id` и без поведения занимает место в типе пункта; вложенность всегда превращается в попап.

**Стало:**

| Компонент   | Что это                                      |
| ----------- | -------------------------------------------- |
| `Item`      | лист навигации: одна цель или действие       |
| `GroupItem` | строка списка, у которой есть дети           |
| `Divider`   | `role="separator"`, пропускается клавиатурой |

`GroupItem` сам решает, как показать детей: развёрнутый рельс → inline-раскрытие, свёрнутый → флайаут. **JSX детей один и тот же.**

Заменяет `menuGroups` + `collapsedMenuGroupIds` + `defaultCollapsedMenuGroupIds` + `onToggleMenuGroupCollapsed` → стандартная пара `expanded` / `defaultExpanded` / `onExpandedChange`.

### 2.4 Оверлеи вынесены из `Item`

**Было:** у пункта семь deprecated-полей про попап (`popupVisible`, `popupRef`, `popupPlacement`, `popupOffset`, `popupKeepMounted`, `renderPopupContent`, `onOpenChangePopup`) плюс `renderFooter` с `asideRef`, который нужен только чтобы попап было к чему прицепить.

**Стало:** `Item` — это строка навигации и больше ничего. Оверлей — отдельный примитив, который объявляется рядом со своим триггером:

```tsx
<AsideHeader.Popup>
  <AsideHeader.Popup.Trigger icon={UserIcon}>Alex</AsideHeader.Popup.Trigger>
  <AsideHeader.Popup.Content><UserCard /></AsideHeader.Popup.Content>
</AsideHeader.Popup>

<AsideHeader.Panel>
  <AsideHeader.Panel.Trigger icon={MagnifierIcon}>Search</AsideHeader.Panel.Trigger>
  <AsideHeader.Panel.Content><SearchPanel /></AsideHeader.Panel.Content>
</AsideHeader.Panel>
```

**Три вещи, которые из этого следуют:**

1. `Popup.Trigger` и `Panel.Trigger` **по умолчанию рендерятся как `Item`** — те же пропы, та же строка рельса, плюс `aria-expanded` / `aria-controls` и подсветка при открытом оверлее.
2. `Popup` — наша обёртка над UIKit-попапом, которая знает про рельс: сегодняшние `mainAxis: 14`, `crossAxis: -30`, `right-start`, `enableSafePolygon` становятся её задокументированными дефолтами. Пользователь получает правильные отступы, ничего не настраивая.
3. Флайаут группы, overflow «More» и попап пункта — **один и тот же `Popup`** с разным контентом. Одинаковое позиционирование и вложенность по построению, а не по совпадению.

**Побочный эффект:** `Item` можно тестировать без единого мока `Popover` / `Drawer`.

### 2.5 Модель активности

Самая содержательная часть — на неё стоит потратить больше времени.

**Было:** один булев `current`, который потребитель считает сам и который напрямую красит пункт. Нельзя выразить «подсвечен, потому что открыта его панель» и «группа подсвечена, потому что активен скрытый потомок».

**Стало:** разведены источники и результат.

```
active = current || открыт попап || открыта привязанная панель
groupActive = флайаут открыт || (есть активный потомок && он не виден)
```

**Правило одной строкой:** подсвечен всегда ближайший **видимый** узел пути.

| Рельс     | Группа         | Подсветка группы | Подсветка потомка |
| --------- | -------------- | ---------------- | ----------------- |
| развёрнут | свёрнута       | полная           | —                 |
| развёрнут | раскрыта       | слабая           | полная            |
| свёрнут   | флайаут закрыт | полная           | —                 |
| свёрнут   | флайаут открыт | полная           | полная            |

**Четыре источника активности, все опциональные:** явный `current`; авто-матчинг `Root.currentPath` + `href`; открытый `Popup`; открытая `Panel`. Последние два бесплатны: триггер оверлея сам знает, открыт ли он.

**Что это даёт бесплатно:** `aria-current`, `aria-expanded`, `aria-controls`, подсветка кнопки «More», когда активный пункт уехал в overflow, авто-раскрытие группы при смене роута.

### 2.6 `Logo` по частям + контракт `Row`

**Было:** монолитный `logo={{icon, text, wrapper, iconSrc, iconClassName, textSize, …}}`.

**Стало:**

```tsx
<AsideHeader.Logo href="/">
  <AsideHeader.Logo.Icon data={logoIcon} />
  <AsideHeader.Logo.Text>Acme Cloud</AsideHeader.Logo.Text>
</AsideHeader.Logo>
```

Плюс общий контракт строки, на котором построены `Item`, `Logo`, `GroupItem.Trigger`, `CollapseButton`:

```
[ Leading 56px ][ Body 1fr ][ Trailing auto ]
  виден всегда   скрыт в compact
```

**Тезис:** «у всех базовых частей заданы дефолты лейаута, поэтому в развёрнутом и свёрнутом состоянии они корректно выглядят из коробки; в остальном — полная свобода». Свой контент кладётся в те же три зоны, либо берёт `useAsideHeaderCompact()` / `WhenCompact` / `WhenExpanded`.

**Важная деталь:** скрытие в compact — только CSS, без размонтирования. Иначе ломаются transition-ы, теряется фокус и расходится SSR-разметка.

### 2.7 Два режима лейаута — гарантии не теряются

Это ответ на главное возражение.

```tsx
<AsideHeader.Root layout="slots">   {/* по умолчанию: строгая раскладка, порядок JSX не важен */}
<AsideHeader.Root layout="manual">  {/* свободная композиция, замена PageLayout */}
```

**Дерево и пропы в обоих режимах одинаковые** — меняется только то, кто расставляет части по местам. Мы не поддерживаем два API.

Слот-метка — Symbol на типе компонента, не строковый `displayName`: не ломается минификацией. Нераспознанные прямые дети → `console.error` в dev с подсказкой про `manual`.

## 3. Что показать в демо

Порядок сторис, если презентация с экраном:

1. `Showcase` рядом со старым компонентом — «выглядит один в один».
2. `CustomTheme` — те же `--gn-aside-header-*` переменные, тема прикладного проекта применяется без изменений.
3. `CollapseButtonWrapper` — `collapseButtonWrapper` → `render`.
4. Сворачивание рельса на группе с активным потомком — подсветка переезжает с ребёнка на группу.
5. `AdvancedUsage` — `layout="manual"`.
6. Dev-консоль с `console.error` на постороннем ребёнке в `slots` — «магия с диагностикой».

## 4. Ожидаемые возражения и ответы

| Возражение                                  | Ответ                                                                                                                                                                                                                                                  |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| «Compound теряет гарантии раскладки»        | `layout="slots"` — дефолт, посторонние прямые дети не рендерятся и дают dev-ошибку. Свободная композиция — явный opt-in.                                                                                                                               |
| «Это переизобретение ради переизобретения»  | Закрывается уже принятый пункт роадмапа «Unify subheaderItem, menuItem, footerItem API». Проверено по коду: три API рендерят один `Item`.                                                                                                              |
| «Слот-магия непрозрачна при отладке»        | dev-`console.error` + `layout="manual"` как аварийный выход. Метка на типе, а не на строке.                                                                                                                                                            |
| «Свой `Composite` — лишний код в поддержке» | base-ui не экспортирует `internals/composite` публично. Наш порт ~210 строк и покрывается тестами. Альтернатива — оставить `List` с `virtualized/sortable/filterable={false}`, ручным расчётом высот и `activateItem(undefined as unknown as number)`. |
| «Breaking change слишком дорогой»           | Новое живёт рядом со старым за отдельным импортом. Есть гайд миграции, инфраструктура codemod-ов в репозитории и возможность временного `AsideHeaderLegacy`.                                                                                           |
| «React 19 обязателен?»                      | `peerDependencies` уже допускают `^19`. Но бамп `@types/react` вскрыл 38 ошибок типов в **старом** коде (в новом — 0). Это отдельное решение, см. вопрос ниже.                                                                                         |
| «Слишком много компонентов запоминать»      | Три уровня использования: `items={[…]}` для миграции, композиция `Item` для 90 % кейсов, `Row`/`render` для нестандартного. Начинать можно с первого.                                                                                                  |
| «Визуальные регрессии»                      | Портированные сторис + существующая инфраструктура Playwright-снапшотов, сверка до переключения.                                                                                                                                                       |
| «Зачем свой `Popup`, есть же uikit-овый»    | Мы его и используем — `AsideHeader.Popup` это обёртка, а не замена. Её задача — знать про рельс: отступы, сторону, поведение в compact, вложенность. Сейчас это те же значения, но зашитые в приватные константы `ItemPopup`.                          |
| «Tab вместо стрелок — регресс»              | Для существующих пользователей да. Но пункты рельса — ссылки, и roving прячет их от Tab: кто табает, проскакивает меню целиком. Возврат к текущему поведению — один проп `keyboard="roving"`.                                                          |

## 5. О чём просим решение

Вынести в конец презентации как список голосований.

1. **Идём или не идём** в compound как в направление мажора.
2. **Имена:** `ItemList` / `GroupItem` / `Popup` / `WhenCompact` — согласовать до кода, переименовывать потом дорого.
3. **`Row` в публичном API** — да или нет.
4. **Фокус-модель рельса:** Tab по каждому пункту (предлагается) или roving tabindex со стрелками, как сейчас. В оверлеях в обоих случаях — стрелки.
5. **`Root.currentPath`** — часть ядра или отдельный адаптер под роутер.
6. **React 19 type fallout:** починить 38 ошибок в старом коде сейчас, отложить или откатить бамп типов.
7. **`AsideHeaderLegacy`** на один мажор — нужен или переключаемся сразу.
8. **Судьба `AllPagesPanel`** и режима редактирования меню: остаётся частью `AsideHeader` или выделяется в отдельный компонент пакета.

## 7. Финальный слайд

> Мы не добавляем ещё один способ настроить `AsideHeader`. Мы убираем шесть из семи и делаем оставшийся единообразным.
>
> Побочный результат: чинятся невалидный ARIA, отсутствующая клавиатура в футере и сабхедере, непозиционируемые попапы и невозможность подсветить пункт по открытой панели.
